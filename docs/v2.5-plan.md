## Locked decisions

1. **Grain** — event-interval stays the atomic unit, enriched with real-machine attribute types. (ADR-0001)
2. **Ingest** — interval CSV is the only input; tag snapshots are reference-only. (ADR-0001)
3. **Prediction** — deterministic what-if + banded trend forecast, **no ML/LLM**. (ADR-0002)
4. **Stop causes** — the machine's native alarm families (Fault, External, Starvation, Buildup, Operator, Supplies, Changeover). (CONTEXT.md)
5. **Impact currency** — bottles lost = time lost × target speed. (CONTEXT.md)
6. **Totals UI** — KPI card tiles + charts; raw tables collapsed into an expander.
7. **AI removal** — full removal of the LLM explainer (`ai.py`, `ai` extra, UI); docs reframed around deterministic math. The "computer does the math" ethos is kept and re-pointed at the predictive model.
8. **Code layout** — consolidate the app at the v2.5 repo root; `LineLens_export/` stays as a frozen v2 reference.

## Proposed interval CSV schema (pending sign-off)

One row per state interval. Built on the current 9 columns + 4 enrichments.

| Column | Status | Meaning |
|---|---|---|
| `machine_id` | existing | e.g. M01 |
| `timestamp_start` / `timestamp_end` | existing | interval bounds |
| `state` | existing | Running / Idle / Stopped / Microstop … |
| `stop_cause` | **renamed** from `stop_reason` | one of the 7 families; blank when running |
| `shift` | existing | A / B / C |
| `recipe` | **new** | product being run (from RCPrn, e.g. "Lampone Zero 560ml") |
| `speed_target` | **new** | target bottles/hr for the recipe (from SpeedTarget) |
| `speed_actual` | **new** | actual bottles/hr this interval (0 when not running) |
| `good_count` / `reject_count` | existing | incremental per interval |
| `planned` | **new** | bool — scheduled stop (break / planned maint) → excluded from Availability |

**Deliberately *not* columns** (they are outputs LineLens computes, or odometers):
`StatusRunningTime`, `AlarmStatus.*Time`, `Bottles_Counter`, `OeeCalculation`,
`Availability/Performance/QualityCalculation`, `ScheduledTimeMinute`.
(`CntMaintenance*`, `AlmNumber`, `DailyBottles` are not needed for v2.5 KPIs; addable later.)

## Proposed fictional dataset (pending sign-off)

Month-long, realistic, grounded in the real export's value ranges (`Data/datatypes to add.txt`).
~16 scheduled hrs/day across 2–3 shifts, 1–2 machines, 2 recipes. Stop-cause mix weighted so a
clear Pareto emerges (Starvation ≫ External > Buildup > Fault > Operator > Supplies) + Changeover
between recipes. Speeds under target (Performance loss); ~0.3–0.5% rejects (Quality ≈ 99.6%).
`good_count = speed_actual × duration`. A gentle OEE drift across the month gives the forecast a
real trend.

## Proposed forecast

Daily OEE & bottles trend extrapolated ~7 days ahead on the production graph, drawn as a line with
a ±1σ shaded band. Never a single confident number.

## Build order

| # | Milestone | Narrowest check after |
|---|---|---|
| **1** | **Consolidate code to root; remove AI; reframe plain-words doc.** | app boots from root with `uv run streamlit run app.py`; no `ai` references remain |
| 2 | Extend `CanonicalRole`/schema for the new columns | new roles map + validate |
| 3 | Generate the fictional month CSV into `sample_data/` | loads + maps cleanly |
| 4 | OEE module (Availability/Performance/Quality/OEE from intervals + `planned` flag) | KPI values match a hand-computed sample |
| 5 | KPI card tiles + Pareto chart (replace tables) | cards render; Pareto ranks by bottles lost |
| 6 | What-if model + sliders fed by the Pareto's top causes | sliding a cause updates OEE→bottles live |
| 7 | Banded forecast on the production graph | band shown; no single confident number |

## Known gaps (flagged during planning)

- **No test suite in `LineLens_export/`.** `pyproject.toml` sets `testpaths=["tests"]` but no
  `tests/` dir and no `test_*.py` exist, despite docs claiming "each check is backed by a test."
  `uv run pytest` currently collects nothing. Decide during the build whether to restore tests
  (the design docs `m4/m5/m7-*.md` are also referenced in code but absent from the export).
- The real one-week machine export is **expected from the user** as reference for naming columns
  and grounding the fictional data (Milestone 3). Not blocking for Milestone 1.
